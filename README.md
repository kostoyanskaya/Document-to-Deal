# AthenAI Document-to-Deal Pilot

Сервис принимает один клиентский документ (PDF / DOCX / TXT) и превращает его в:

1. структурированную **карточку лида** (JSON, валидируется Pydantic-схемой);
2. короткий **аналитический бриф** (Markdown);
3. **черновик коммерческого предложения** (Markdown).

Всё остаётся в статусе `draft`. Автоматической отправки в CRM или клиенту нет —
есть только ручной `/approve`, который меняет статус задачи и ничего не отправляет.

> Демонстрационный модуль: не использует реальные данные, ключи или CRM.
> Всё, включая `examples/`, — синтетика.

---

## Технологии и почему они выбраны

| Что | Почему |
|---|---|
| **FastAPI + Pydantic v2** | Валидация входа/выхода "из коробки", автогенерация OpenAPI, асинхронность нативно. |
| **Celery + Redis** | Обработка документа (парсинг + вызовы LLM) не блокирует запрос и может занимать секунды. Celery — стандарт для такой очереди в проде (retry, конкурентность, мониторинг), Redis один закрывает три роли: брокер задач, хранилище идемпотентности и хранилище статусов — не нужен отдельный Postgres под объём одного пилота. |
| **LLM-адаптер с mock-режимом** | Проект должен запускаться и проходить тесты без API-ключа. `MockLLMAdapter` — не заглушка сети, а детерминированный rule-based экстрактор, поэтому даже без ключа выдаёт правдоподобный результат. Реальные провайдеры (OpenAI, DeepSeek) подключаются одной строкой в `.env`. |
| **Два отдельных вызова LLM** | Вызов 1 (`extraction`) видит сырой текст документа и возвращает только типизированный JSON. Вызов 2 (`generation`) видит уже провалидированную карточку лида и больше никогда не читает сырой текст — это сужает то, как содержимое документа может повлиять на итоговый Markdown. |
| **Трёхслойная защита от prompt-инъекций** | Слой 1 — regex/keyword сканер (быстро, бесплатно, ловит явные паттерны). Слой 2 — LLM-as-judge: отдельный вызов модели, который только классифицирует текст и ничего не выполняет, ловит перефразированные атаки, которые обходят regex; при сбое или некорректном ответе — fail closed (документ не пропускается). Слой 3 — проверка сгенерированного brief/proposal на дословную утечку системного промпта перед отдачей наружу. Ни один слой не заменяет остальные — подход соответствует текущим рекомендациям OWASP по LLM (defense-in-depth, а не единственный guardrail). |
| **Идемпотентность по SHA-256 файла** | Побайтово одинаковая повторная загрузка возвращает существующую задачу вместо дубликата. Завязано на содержимое, а не на имя файла — переименование не обходит проверку. |
| **Docker Compose** | Запуск одной командой без ручной настройки Redis/окружения. |

## Быстрый старт

```bash
cp .env.example .env
docker compose up --build
```

- API: http://localhost:8000 (демо-UI на `/`, документация на `/docs`)
- По умолчанию `LLM_PROVIDER=mock` — API-ключ не нужен.

```bash
# Обычный документ -> completed
curl -F "file=@examples/normal_brief.txt" http://localhost:8000/api/v1/documents
curl http://localhost:8000/api/v1/tasks/<task_id>

# Документ с prompt-инъекцией -> blocked, LLM не вызывается
curl -F "file=@examples/injection_attempt.txt" http://localhost:8000/api/v1/documents
curl http://localhost:8000/api/v1/tasks/<task_id>
```

## Тесты

```bash
pip install -r requirements-dev.txt
pytest -q
```

Redis и API-ключ не нужны: Redis подменяется `fakeredis`, Celery работает в
eager-режиме, LLM — в mock-режиме. Отдельный набор тестов (`tests/test_injection_detector.py`,
`tests/test_security_extra.py`) покрывает prompt-инъекции на русском и
английском, включая контрольный тест на безобидный документ (чтобы
случайный URL сам по себе не блокировал заявку).

## Переключение LLM-провайдера

```bash
# .env
LLM_PROVIDER=mock       # по умолчанию, офлайн, ключ не нужен

LLM_PROVIDER=openai
OPENAI_API_KEY=sk-...
OPENAI_MODEL=gpt-4o-mini

LLM_PROVIDER=deepseek
DEEPSEEK_API_KEY=...
DEEPSEEK_MODEL=deepseek-chat
DEEPSEEK_BASE_URL=https://api.deepseek.com
```

`DeepSeekAdapter` переиспользует OpenAI SDK против OpenAI-совместимого
эндпоинта DeepSeek — отдельная клиентская библиотека не нужна. Новый
провайдер = реализация `LLMAdapter` (`complete_json`, `complete_text`) +
одна ветка в `get_llm_adapter()`.

## Машина состояний

```
queued → processing → blocked          (найдена инъекция, стоп)
                     → needs_review     (неоднозначный сигнал, стоп)
                     → completed        (карточка лида + бриф + КП готовы)
                        → approved      (вручную, через POST /approve)
                     → failed           (ошибка LLM/парсинга после ретраев)
```

Автоматического перехода в «отправлено» нет — такого статуса не существует
по замыслу.

## Модель угроз

| Угроза | Митигация |
|---|---|
| Prompt-инъекция в документе (переопределение инструкций, попытка получить системный промпт, запуск команд/кода, фишинговые ссылки) | 3 слоя (см. выше). Документы со статусом `blocked`/`needs_review` не доходят до генерации — карточка лида/бриф/КП не создаются. |
| LLM возвращает невалидный JSON | Pydantic-валидация с ретраями (`LLM_MAX_RETRIES`); при исчерпании попыток — `status=failed`, невалидные данные наружу не отдаются. |
| Повторные отправки создают дубликаты задач | Идемпотентность по `SHA-256(файл) → task_id` с атомарным Redis `SET NX`, TTL 24ч. |
| Слишком большие/неверные файлы (DoS-вектор) | Allowlist расширений (`.pdf/.docx/.txt`) + потоковая проверка лимита `MAX_FILE_SIZE_MB`; файл не передаётся парсеру, пока размер не прошёл проверку. |
| Утечка секретов/текста документа в логи | В логи пишутся только длины, усечённые хеши, статусы/вердикты и типы ошибок — никогда ключи, сырой текст документа или полные ответы LLM. |
| Случайная отправка клиенту/в CRM | В кодовой базе нет пути отправки — `/approve` только меняет статус. |

**Вне рамок пилота** (см. ниже): аутентификация, антивирус для файлов,
rate limiting, полноценный audit trail, production-хранение секретов.

## Что нужно для продакшен-версии

- **Auth** — сейчас все эндпоинты открыты. Нужны как минимум API-ключи или
  OAuth2 со скоупингом по тенантам; CORS `*` заменить на реальный список origin'ов.
- **Антивирус/песочница для файлов** — парсинг PDF/DOCX сейчас доверяет
  библиотекам-парсерам без проверки на вредоносное содержимое. Нужен
  AV-скан (например, ClamAV) и/или парсинг в изолированном воркере без
  исходящей сети.
- **Rate limiting** — сейчас ничего не ограничивает число загрузок или
  расходы на LLM на клиента/IP. Нужны лимиты на тенанта/IP (обратный прокси
  или `slowapi`/Redis token bucket).
- **Audit trail** — сейчас история задачи в Redis перезаписывается на
  месте без хранения истории. Нужен append-only журнал (таблица в Postgres
  или поток событий) с привязкой актора к каждому переходу статуса,
  особенно к `approve`.
- **Управление секретами** — `.env` годится только для локальной демонстрации.
  Нужен полноценный секрет-менеджер (Vault, AWS/GCP Secrets Manager),
  ротация ключей, отсутствие plaintext-ключей в конфигах деплоя.
- Дополнительно стоит учесть: централизованное логирование с редактированием
  PII, лимиты размера запроса на уровне прокси, защиту от zip/PDF
  decompression bombs, мониторинг стоимости LLM по провайдерам, отдельное
  явно аудируемое действие «send» в CRM (пилот его намеренно не реализует).

## Заметки

- Python 3.11+, FastAPI, Pydantic v2, Celery 5, Redis 7.
- `openai` SDK используется и для OpenAI, и для DeepSeek (совместимый API);
  в mock-режиме не импортируется вовсе.
- OpenAPI генерируется автоматически: `/docs`, `/openapi.json`.
